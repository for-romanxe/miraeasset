## 세션 2 — 챗봇·멀티에이전트 아키텍처 발표 (28장)

우리 설계 검증에 가장 중요한 세션. 요지:

- **문제의식**: 데모(정형 질문)와 실서비스(주어 생략·복합 질문)의 괴리. LLM 만능주의 →
  프롬프트 비대화·Prompt Drift. 금융권 오답은 법적 분쟁(Air Canada, Chevrolet 사례).
  목표는 "그럴듯한 답"이 아니라 **검증 가능성**
- **LLM이 틀리는 이유**: 정보량 부족이 아니라 **모호성 미해결**. Context 3요소 = 대화 이력·사용자 프로필·외부 지식
- **멀티에이전트 실패 분류(MAST)**: 시스템 설계 44.2% / 에이전트 간 정렬 32.3% /
  **검증 실패 23.5% — 금융권에서 최악의 유형**
- **해결책**: 환각 = Specification Failure. 오케스트레이터는 "답변기"가 아니라
  명세를 만들고 명세대로 실행을 통제하는 **작업 반장**
- **4단계 파이프라인**: Rule 처리 → 쿼리 분석(명세 생성) → Task 수행(실행/검증) → Response
- **모호성 처리 두 경로**: Clarify(되묻기) vs **Assume+Expose(가정을 명시하고 답하기)**
- **Response 정책**: 결과·근거·가정·다음 행동 + 근거 없는 답변 차단 + 안전한 Fallback
- **운영**: Iterative disambiguation — 로그 수집 → 모호성 분석 → 명세 강화 → **회귀 테스트**

### 판독 보완 (원본 사진 재판독, 2026-08-07)

**23장 — "내 IRP 계좌 한 달 수익률" 처리 예시 (3단계 라우팅)**
1. 가드레일: Risk 평가(개인 계좌 정보 접근 = 위험도 중간) + 인증 상태 확인 → Pass
2. 질의 분석: 컨텍스트 결합(질문+인증상태) → **슬롯 추출(Target: IRP / Action: 수익률 조회 /
   Condition: 한 달)** → 라우팅 매핑(에이전트 후보 중 2번 확정) → **명세 작성
   ("모호성 해결: '최근 30일 기준' 명시" / "API 결괏값 반드시 포함")**
3. 실행·검증: 업무처리 에이전트가 API 조회 → **Verifier가 명세 대조**(30일 기준 명시 확인,
   API 값 포함 확인) → 최종 승인
- 인용: "오케스트레이터는 철저한 쿼리 분석과 명세서에 따라 에이전트를 지휘하는 '경영자'"

**24장 — 라우팅 판단 축 5개 (Decision Axes)**
1. **Cost**: "LLM을 안 태우고 캐시/룰로 끝낼 수 있는가?" (비용 최적화)
2. **Intent**: 내 계좌 → 업무처리·맞춤상담 / 일반 정보 → 단순조회·상품조회
3. **Context**: 인증 완료 → 계좌 에이전트 호출 가능 / 미인증 → 차단 또는 일반 에이전트 우회
4. **Risk**: 단순 조회 = 저위험 / 맞춤 상담 = 고위험(환각 주의)
5. **Ambiguity**: 질문이 모호한가? → Clarifier(되묻기) 호출
- 플로우: 질문 입력 → 1차 Intent → 2차 Context → 3차 Risk & Ambiguity →
  에이전트 선택(단순조회/업무처리/맞춤상담/상품조회)

## 우리 설계와의 대조

| 발표 내용 | 우리 상태 |
|---|---|
| 4단계 파이프라인 (Rule → 분석 → 수행 → Response) | 라우터 → 검색/계산 → 생성 구조와 일치 ✅ |
| Cost 축: 룰로 끝낼 수 있으면 LLM 안 태움 | 키워드 라우터·가드레일 선처리와 일치 ✅ |
| Clarify(되묻기) | 역질문 분기 구현됨 ✅ |
| 근거 없는 답변 차단 + 안전한 Fallback | 가드레일·한계 고지 구현됨 ✅ |
| 회귀 테스트 중심 운영 | 평가셋 105문항 하네스 ✅ |
| **Verifier: 답변-명세(근거) 대조 검증** | **미구현 — 최우선 과제로 격상** ⚠️ |
| **Assume+Expose** (가정 명시 후 답변) | **미구현 — 역질문 남발 방지용으로 추가** ⚠️ |
| 슬롯 추출(Target/Action/Condition) 명세화 | 라우터 HCX 전환 시 이 스키마 채용 예정 |

  단 **답변 생성 플로우는 HyperCLOVA 필수** (임베딩은 명시 언급 없음 — 디스코드로 확인)

  **대표 팀원에게 Org 초대장** → 대표가 팀원을 컬래버레이터로 초대 → 그 레포에 제출.

  전체 커밋 히스토리를 확인 가능한 상태로 푸시 권장
- API 호출 시점·서버 운영 기간은 추후 공지 예정 (특정 시간대에 엔드포인트 활성화)

### 도메인 설명 파트 요지

- DB=회사가 운전하는 버스, DC=내가 운전하는 자가용 비유. IRP는 퇴직금 받는 그릇 +
  추가납입. 연금계좌는 상품이 아니라 그릇 — 안에서 예금·펀드·ETF를 다시 선택
- 과제 투자설명서 데이터는 **전부 실적배당형**
- 상품 비교 시 볼 축: 보수(비용)·과거 성과·운용 규모 — funds.json 6축과 일치
- 외부 데이터: 기본 연금 제도 자료에 한해 수집 자유, 단 **답변 근거는 제공 문서
  안에서 확보**되어야 하고 상충 시 제공 데이터 우선 (재확인)
- 운영진이 직접 강조: "데이터로 답할 수 없으면 확정적 답변 대신 **역질문하는
  케이스가 굉장히 필요**" — 정보한계 대응이 채점에서 실제로 중요함을 재확인
