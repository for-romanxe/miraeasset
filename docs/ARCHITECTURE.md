# 연금 Agent 설계안 (v0 초안 — 팀 논의용)

## 평가 방식에서 역산한 원칙

주최 측이 우리 API에 비공개 질문을 쏘고 `retrieved_context / think_trace / answer`를 채점한다.
평가지표(정확성·근거 완전성·환각 방지·역질문 대응)를 보면 이 Agent의 본질은
**"근거를 정확히 찾고, 못 찾으면 못 찾았다고 말하는 시스템"** 이다.

- 수치 계산은 LLM에게 시키지 않는다 → 파이썬 함수로
- 단정 추천 금지·역질문은 프롬프트가 아니라 코드 분기로
- 모든 답변에 근거 문서·페이지 표시 (데이터에 마커 이미 있음)

## 파이프라인

```
질의 → ① 라우터 → ② 검색/조회 → ③ 계산 → ④ 답변 생성 + 가드레일
```

| 단계 | 역할 | v0 (뼈대) | 목표 버전 |
|---|---|---|---|
| ① router | 질의 유형(제도/세제/상품/종합/절차) 분류, 필요 조건 슬롯 판정 | 키워드 규칙 | HyperCLOVA X 분류 + 슬롯 추출 |
| ② retriever | docs 58건 검색 + funds.json 정형 조회 | BM25 + 이름/필터 매칭 | 하이브리드(BM25+임베딩), 시리즈 비교 |
| ③ calculator | 세액공제·연금소득세 등 규칙 계산 | 세액공제 한도 1종 | 세제 계산기 풀세트 |
| ④ generator | 근거 기반 답변 생성, 근거 인용 강제 | Mock LLM | HyperCLOVA X + self-check |

- 상품 질의의 수치 비교·정렬·필터는 임베딩 검색이 아니라 **funds.json 코드 필터링**으로 처리
- "좋은 상품 추천해줘"처럼 조건이 빈 질의는 검색으로 가지 않고 **역질문 분기**
- 종합 질의(예: 명퇴 교사 절세)는 docs 검색 + 계산기를 함께 사용

## 모듈 구조 (agent/)

```
server.py            GET /answer 엔드포인트 (평가 스키마 그대로)
llm.py               LLM 인터페이스. MockLLM(현재) ↔ HyperClovaX(8/6 이후 교체)
data.py              funds.json / docs 로딩
pipeline/
  router.py          질의 분류 + 슬롯 판정
  retriever.py       DocsIndex(BM25) + FundsIndex(정형 필터)
  calculator.py      세제 계산기
  generator.py       프롬프트 구성 + 생성 + 가드레일
```

인터페이스가 고정돼 있으므로 모듈별 병렬 작업 가능. LLM 호출부는
`generate(prompt) -> str` 하나로 통일해서 8/6 크레딧 수령 후 갈아 끼운다.

## 응답 스키마 (과제 명세 준수)

```json
GET /answer?question_id=Q-001&question=...
{
  "question_id": "Q-001",
  "question": "평가 질의 원문",
  "retrieved_context": "근거 문서 발췌 (출처 라벨 포함)",
  "think_trace": "[라우팅] ... [검색] ... [계산] ... [생성] ...",
  "answer": "최종 답변 (근거 표시 포함)"
}
```

## 규칙 관련 주의

- 서비스 내 LLM은 HyperCLOVA X만. 개발 도구(Claude 등)는 무관
- 임베딩 모델은 회색지대 → CLOVA Studio 임베딩 또는 로컬 오픈소스 사용, 디스코드로 확인
- 외부 데이터는 제도 자료 보조로만, 제공 자료와 충돌 시 제공 자료 우선
