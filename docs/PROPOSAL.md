## 1. 제안 요약

**"근거를 정확히 찾고, 못 찾으면 못 찾았다고 말하는 연금 상담 Agent"**

제공된 연금 안내문서 58건과 투자설명서 100건만을 근거로, 제도·세제·상품·절차 질의에
답하는 단일 엔드포인트 API 서버입니다. 설계의 중심에는 세 가지 결정이 있습니다.

1. **숫자는 코드가 계산하고, 언어는 HyperCLOVA X가 만든다** — 세액공제 한도, 연금소득세율,
   연금수령한도 같은 수치는 LLM 생성이 아니라 문서 규칙을 옮긴 파이썬 함수가 계산합니다.
2. **답변이 아니라 검증을 마지막 단계에 둔다** — 생성된 답변의 모든 수치 토큰이 검색 근거
   안에 실재하는지 코드가 대조한 뒤에야 응답이 나갑니다.
3. **모호한 질문에 단정하지 않는다** — 조건이 빠진 추천 질의는 검색·생성을 거치지 않고
   역질문으로, 보유 데이터 범위 밖 질의는 한계 고지로 분기합니다.

이 셋은 모두 프롬프트 지시가 아니라 **코드 분기와 검증 단계로 구현**되어 있습니다.
프롬프트는 지켜지지 않을 수 있지만 코드는 지켜지기 때문입니다.

## 2. 문제 정의

### 2.1 연금 상담은 "그럴듯한 답"이 가장 위험한 도메인이다

연금 질의의 답은 대부분 **숫자**입니다 — 세액공제 900만원, 연금소득세 5.5%, 퇴직소득세
감면 40%. 그런데 이 숫자들은 계좌 종류·나이·수령 연차·납입 이력에 따라 달라지고,
질문자는 대개 그 조건을 말해주지 않습니다.

여기서 범용 LLM은 세 가지 방식으로 실패합니다.

| 실패 유형 | 구체적 양상 | 실제 위험 |
|---|---|---|
| **수치 환각** | 그럴듯하지만 문서에 없는 세율·한도를 생성 | 고객의 실제 금전 손실. 금융사 답변은 법적 책임을 동반 |
| **모호성 미해결** | 조건이 빠진 질문에 임의 가정으로 단정 답변 | 잘못된 상품 추천 = 불완전판매 |
| **잘못된 전제 수용** | "명퇴수당 넣으면 세금 감면 어마어마하다던데"의 전제를 그대로 승인 | 오해를 확증해주는 답변 |

금융 챗봇의 오답이 법적 분쟁으로 이어진 해외 사례(Air Canada, Chevrolet)가 보여주듯,
이 도메인에서 요구되는 것은 유창함이 아니라 **검증 가능성**입니다.

### 2.2 평가지표에서 역산한 요구사항

과제 자료가 제시한 평가지표 7종은 위 문제의식과 정확히 일치합니다. 저희는 각 지표를
"어떤 코드가 이것을 보장하는가"로 번역하여 설계했습니다.

| 평가지표 | 설계상의 대응 |
|---|---|
| 정확성 (수치·비교 정확, 잘못된 전제 교정) | 계산기 7종 + 전제 교정 분기 |
| 근거 완전성 (필수 근거 포함, 무관한 근거 배제) | BM25 검색 + 펀드명 오매칭 차단 규칙 |
| 요구사항 충족 (누락 없이 응답) | 복합 질의에서 검색·계산 병행 |
| 근거 기반 (Hallucination 방지) | **Verifier: 답변 수치 ↔ 근거 대조** |
| 추론 논리성 | `think_trace`에 단계별 판단 기록 |
| 안전성·신뢰성 (개인정보·프롬프트 공격) | 가드레일 선분기 |
| 정보한계 대응 (한계 고지 또는 역질문) | 한계 고지 분기 + 역질문 분기 |
| 모든 답변에 근거 문서 표시 | 코드가 출처를 강제 부착 |

## 3. 제안 방법

### 3.1 설계 원칙 네 가지

**① 숫자는 코드가, 해석은 AI가**

LLM에게 원문 표를 주고 합계를 시키지 않습니다. 세제 계산은 문서에 명시된 규칙을 옮긴
순수 함수 7종이 담당하고, LLM은 그 결과를 사람의 언어로 설명하는 역할만 합니다.
각 계산 결과에는 근거 문서 번호가 함께 반환되어 출처 표기까지 자동으로 이어집니다.

**② 근거 없는 답변을 구조적으로 차단**

검색 결과가 없으면 생성 단계로 넘어가지 않습니다. 생성 후에도 Verifier가 답변의 수치를
근거와 대조하며, 대조되지 않는 수치가 있으면 답변에 재확인 안내를 덧붙입니다.

**③ 모호성은 프롬프트가 아니라 분기로 처리**

"좋은 연금 상품 추천해주세요"는 계좌·위험성향·투자기간 세 슬롯이 모두 비어 있습니다.
이때 검색을 수행하면 반드시 무언가는 검색되고, LLM은 그것으로 답을 만들어냅니다.
따라서 **검색 이전에** 슬롯을 판정해 역질문으로 분기합니다.

**④ 처리 과정을 응답에 노출**

`think_trace` 필드에 라우팅 판정, 검색된 문서와 점수, 계산기 입출력, 검증 결과를
단계별로 기록합니다. 평가자가 답변의 근거뿐 아니라 **도출 경로까지 검산**할 수 있습니다.

### 3.2 왜 벡터 검색이 아니라 BM25인가

지식베이스가 문서 58건(청크 431개) 규모이고, 질의가 제도 용어 중심이라 어휘 매칭의
정밀도가 높습니다. 여기에 형태소 분석기 없이도 조사·어미 변형을 흡수하도록
**어절 + bigram + trigram 혼합 토큰화**를 적용했습니다.

- 한글 어절은 2회 가중(온전한 매칭 우대), n-gram은 1회(재현율 확보)
- 영문 약어(IRP·DC·ETF)는 3회 — 변별력이 가장 높으나 한글 bigram에 묻히기 쉬움
- 맨 숫자는 1회, 단 `100%` 같은 백분율은 통째로 하나의 토큰

임베딩 검색은 이 규모에서 정확도 이득이 불확실한 반면 규정 회색지대(런타임 HyperCLOVA X
전용 규정)에 해당하므로, **확인 전까지 채택하지 않는 보수적 선택**을 했습니다.

## 5. 주요 기능 흐름도

### 5.1 처리 순서와 조기 분기

```
질의 도착
   │
   ├─▶ [안전성 판정] 개인정보 요구·프롬프트 공격인가?
   │        └─ YES ─▶ 정중한 거절                        ⟶ 종료 (검색 없음)
   │
   ├─▶ [범위 판정] 보유 데이터 밖(공적연금·실시간 시세·개인 계좌)인가?
   │        └─ YES ─▶ 한계 고지 + 담당 기관 안내          ⟶ 종료 (검색 없음)
   │
   ├─▶ [슬롯 판정] 추천 질의인데 계좌·위험성향·기간이 비었는가?
   │        └─ YES ─▶ 역질문 (확인 항목 제시)             ⟶ 종료 (검색 없음)
   │
   ├─▶ [상품 조회] 질의에 펀드명이 있는가?
   │        └─ YES ─▶ funds.json 토큰 매칭
   │                   └─ 비교 질의 + 2건 이상 ─▶ 6축 비교표 생성
   │
   ├─▶ [문서 검색] BM25 상위 5개 청크 (문서당 최대 2개)
   │
   ├─▶ [계산] 세제 질의면 해당 계산기 실행 (금액·나이·연차 추출)
   │
   ├─▶ [생성] HyperCLOVA X — 근거 블록만으로 답변 작성
   │
   ├─▶ [검증] 답변 수치가 근거에 실재하는지 대조
```

조기 분기 3종이 **검색 이전**에 놓인 것이 핵심입니다. 검색을 먼저 하면 무언가는 반드시
검색되고, 그 순간 답변을 만들지 않을 이유가 사라지기 때문입니다.

모두 순수 함수이며, 반환값에 계산 과정 문자열과 근거 문서 번호가 포함됩니다.

| `pension_income_tax` | 연령별 연금소득세율 5.5%·4.4%·3.3% | doc38 |
| `retirement_tax_discount` | 퇴직소득세 감면 30%, 11년차부터 40% | doc51 |
| `pension_withdrawal_limit` | 평가액÷(11−연차)×120%, 11년차 이상 무제한 | doc39 |
| `early_withdrawal_tax` | 부득이한 사유 판정 → 연금소득세 / 아니면 16.5% 기타소득세 | doc20·46–50 |
| `private_pension_tax_comparison` | 사적연금 1,500만원 문턱 분리과세 vs 종합과세 비교 | doc38 |

## 6. 사용자 시나리오

과제 자료의 참고 질의 set을 실제 시스템에 입력한 결과입니다.
아래 `think_trace`와 답변 본문은 실제 시스템 출력이며 임의로 다듬지 않았습니다.

### 시나리오 A — 정상 답변 (세제, 난이도 하)

> **"연금저축이랑 IRP에 넣으면 세액공제 얼마까지 되나요? 다 합쳐서요."**

```
[라우팅] 유형=세제,제도
[검색] doc23 본문(score 65.29), doc41 본문(score 64.41), doc41 본문(score 63.6),
       doc33 슬라이드 6(score 62.2), doc44 본문(score 57.76)
[계산] 금액 미제시 → 한도 정보만 근거로 제공
[생성] LLM=hyperclova-x, 근거블록 5개
[검증] 답변 수치 15개 중 15개 근거 확인
[검증2] all 범위 6문장 검증, 미지지 0건
```

실제 응답:

> 연금저축과 IRP에 돈을 합쳐서 넣었을 때의 세액공제 한도는 **연 900만 원**입니다.
> 다만, 연금저축 계좌에는 연 600만 원, IRP 계좌에는 연 300만 원이 기본적으로
> 세액공제 대상이고, ISA 만기 자금을 연금저축이나 IRP로 전환하여 납입할 경우 그
> 금액의 10%(최대 300만 원)를 추가로 세액공제받을 수 있습니다.
>
> 따라서, 연금저축에 600만 원을 넣고, IRP에 300만 원을 넣었다면 추가로 300만 원을
> 더 넣어 최대로 세액공제를 받을 수 있으며, 이때 세액공제율은 소득 구간에 따라
> 13.2% ~ 16.5%가 적용됩니다. 만약 총 급여 혹은 종합소득금액이 5,500만 원 이하라면
> 최대 148만 5천 원까지 세액공제를 받을 수 있고, 그렇지 않다면 최대 118만 8천 원까지
> 공제될 것입니다.
>
> 단, 이러한 세액공제 한도와 조건은 개인의 소득 상황 및 세부 사항에 따라 달라질 수
> 있으니 자세한 사항은 전문가와의 상담을 통해 확인하는 것을 권장 드립니다. (doc41, doc33)
>
> 근거: doc23(ISA 만기 자금 연금계좌 전환납입 절세 혜택 안내) 본문 /

디폴트옵션 40문항은 주최 측 참고 자료(doc29)의 문답 25건과 그 유사 표현 15건에서

채점은 LLM 판정이 아니라 **결정적 검사**입니다 — 기대 문서가 근거에 인용되었는지,
기대 펀드가 전부 인용되었는지, 역질문 분기가 발생했는지, `think_trace`에 계산 결과가
있는지, 답변에 출처 표기가 있는지. 따라서 LLM의 출력 변동과 무관하게 재현됩니다.

### 8.1 평가지표 7종 × 방어 장치 × 검증 근거

| 평가지표 | 방어 장치 | 저장소 내 검증 근거 |
|---|---|---|
| 정확성 | 문서 규칙을 옮긴 계산기 7종, 잘못된 전제 교정 | `eval/test_calculator.py`, 세제 30문항·전제교정 9문항 |
| 근거 완전성 | BM25 제목 부스트, 펀드명 오매칭 차단, 기대 문서·펀드 대조 | `eval/test_retriever.py`, 전체 평가의 `expect.docs`·`expect.funds` 검사 |
| 요구사항 충족 | 복합 질의에서 검색·계산을 함께 수행하고 조건별 답변 분기 | 복합 8문항·조건부추천 11문항 |
| 근거 기반 | 답변 수치와 검색 근거의 결정적 대조, 문장 단위 Verifier | `eval/test_verifier.py`, 검증 2문항·출처 2문항 |
| 추론 논리성 | 라우팅→검색→계산→검증의 판단을 `think_trace`에 순서대로 기록 | `eval/run_eval.py`의 `trace_contains` 검사 |
| 안전성·신뢰성 | 개인정보·프롬프트 공격·정상 질문 오탐을 라우팅 전에 분리 | 안전성 6문항·가드레일 오탐 2문항, 합계 8/8 통과 |
| 정보한계 대응 | 개인 데이터·시장 전망은 한계를 고지하고, 추천 조건 누락은 역질문 또는 가정 명시 | 정보한계 5문항·조건부추천 11문항 |

위 근거를 포함한 결정적 회귀 평가는 **177/177**이며, 단위 테스트는 **53개 통과
(환경 의존 1개 건너뜀)**입니다. 새 기능은 해당 지표의 평가 문항과 함께 추가하므로
설계 주장과 실행 검증이 같은 저장소에서 추적됩니다.

이 하네스가 실제로 잡아낸 회귀의 예:

- "연금저축 400만원 세액공제" 질의가 **연금저축이라는 이름을 가진 펀드**를 근거로 인용 →
  펀드명 매칭에서 계좌 유형 단어를 제외하도록 수정
- "4주가 지나기 전에" 질의가 주가 전망 질의로 오분류 → 가드레일 패턴을 문맥 한정으로 정밀화

### 9.1 기대효과

| 관점 | 내용 |

| **컴플라이언스** | 단정 추천을 코드가 차단하고 모든 답변에 근거가 부착됨. `think_trace`로 사후 감사 가능 |

**토큰을 사용하지 않는 로컬 실측(2026-09-01, 177문항)**

| 항목 | 실측값 | 해석 |
|---|---:|---|
| 콜드스타트 | import 237ms + 첫 질의 263ms | 서버 시작 후 첫 요청의 로컬 인덱스 준비 비용 |
| 로컬 파이프라인 처리량 | 167.7문항/초 | 라우팅·검색·계산·결정적 검증, LLM 호출 제외 |
| 로컬 지연 | p50 6.1ms / p99 12.7ms | HCX 네트워크·생성 시간과 분리한 시스템 자체 지연 |
| 수동 QA 운영 추정 | 100문항 약 20~25분, 약 500원 | 기존 배치 실행 기록 기준; 문항당 약 5원 |
| 월 1만 문항 환산 | 약 5만원 | 동일한 평균 사용량을 가정한 단순 비례 추정 |

원가 환산은 모델 응답 길이와 재시도 횟수에 따라 달라지는 **운영 추정치**이며, 로컬
p50/p99는 HCX 종단간 지연으로 오인하지 않도록 분리해 표기했습니다. 종단간 지연은 배포
환경에서 `eval/load_test.py`로 다시 측정합니다.

**"AI를 빼면 무엇이 사라지는가"** — 라우팅 판단, 자연어 서술, 한계 고지 표현이 사라지고
전문가만 쓸 수 있는 계산기와 검색 엔진이 남습니다. 반대로 **AI만 남기면** 검증되지 않은
수치를 유창하게 말하는 시스템이 됩니다. 두 축이 모두 필요합니다.

### 9.2 확장성

**구조적 확장** — 파이프라인 각 단계가 인터페이스로 분리되어 있어 개별 교체가 가능합니다.

| 확장 방향 | 방법 | 비고 |
|---|---|---|
| 지식 범위 확대 | 문서 추가 → 파서 재실행 | 코드 변경 없음 |
| 검색 정밀도 | BM25 + 임베딩 하이브리드 | 규정 확인 후 |
| 라우터 고도화 | 키워드 규칙 → HyperCLOVA X 슬롯 추출 | 프롬프트 초안 작성 완료 |
| 검증 심화 | 수치 대조 → 주장 단위 의미 검증 | 인터페이스 마련됨 |
| 개인화 | 계좌 조회 API 연동 시 잔액 기반 계산 | 인증·권한 설계 필요 |

**운영 확장** — 응답 로그의 `think_trace`를 수집하면 어떤 질의에서 검색이 실패했고 어떤
질의가 역질문으로 빠졌는지 집계할 수 있습니다. 이를 평가셋에 되먹여 회귀 테스트를
강화하는 순환 구조(Iterative disambiguation)가 그대로 성립합니다.
